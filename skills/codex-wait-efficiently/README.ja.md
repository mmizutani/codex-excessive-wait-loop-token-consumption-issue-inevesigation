# Codex Efficient Waiting

[English](README.md)

`codex-wait-efficiently` は、サブエージェント、長時間のコマンド、CI などの完了待ちで発生する不要なモデル呼び出しを減らすための Codex スキルです。このリポジトリで検証した待機ルールをスキルとして利用できるようにし、実測に基づいて一部の指示を明確にしています。現在の推奨版は [SKILL.md](SKILL.md) にある **v4** です。

## 要点

- 適切な待機ツールや監視スクリプトを使い、状態が変わっていない間にモデルが何度も確認する動作を減らすことを目指します。
- 新たな Astra の 18 試行では、最終版の導入によって全体のモデル応答数が **36.00%**、入力トークンが **33.53%**、API 単価による換算額が **27.93%** 減りました。一方、CI 単独では換算額が **12.87% 増加**し、結果の通知も遅くなりました。

## このスキルを作った背景

Codex はコマンドやサブエージェント、CI の完了を待つ間、モデルに何度も制御を戻して状況を確認することがあります。状態に変化がなくても、モデルが応答するたびに入力コンテキストの処理と出力の生成が発生し、トークンを消費します。入力キャッシュによって入力の単価が下がっても、不要な応答を重ねることによる消費は残ります。今回検証した Codex CLI 0.154.0 でも、ランタイムの修正だけでは解消されていない待機動作がありました。

このスキルは、待機ツールの選び方と監視処理の組み立て方を Codex に指示します。状態確認を一つの監視スクリプトにまとめれば、毎回モデルを呼び出さずにシェル内で繰り返し確認できます。コマンドは既存のセッションを保持して出力や終了を待ちます。具体的な指示と狙いは次の表にまとめています。

待機ルールをグローバル AGENTS.md に常時適用する代わりに、タスクに応じてスキルを選択させたいユーザー向けに用意しました。Codex はスキル名と説明を手がかりに選択し、使用時に指示本文を読み込みます。実測には、その読み込みに使ったトークンも含めています。

## 期待する効果と動作

| 場面 | 主な指示 | 狙い |
| --- | --- | --- |
| サブエージェント | 既存の子エージェントを `wait_agent` で待ち、待機を含む委任では子にもスキルの使用を依頼する。 | 状態確認の繰り返しを減らし、子エージェントにも待機ルールを適用する。 |
| 長時間のコマンド | プロセスのセッションを保持し、`exec_command` / `write_stdin` で適切な時間待つ。 | 短いポーリングでモデルに何度も制御が戻るのを抑える。 |
| Code Mode | 外側の `functions.exec` が内側のコマンド待機をカバーし、実行中のセルは `functions.wait` で再開する。 | ラッパーが早く戻るためだけに発生するモデル応答を減らす。 |
| CI・外部ジョブ | 完了通知を優先し、通知がなければ時間または確認回数に上限を設けた一つの監視スクリプトにまとめる。 | シェル内で確認を繰り返し、対象ジョブとユーザーが指定した観測上限を維持する。 |
| 完了処理・応答性 | 独立して進められる作業を先に行い、必要な進捗報告と検証を保って実際の結果を伝える。 | 依頼された作業を完了させながら、待機中の不要な処理を減らす。 |

上位の指示、必要な進捗報告、検証は維持します。進捗報告が 60 秒間隔で求められる場合は、報告の時間を確保するため、一度の待機を 45 秒以内に抑えます。効果が未測定のキャッシュ維持だけの呼び出しは追加せず、観測時間の終了とジョブの失敗を区別します。`/goal` が長期の外部依存待ちになる場合は、一時停止について確認し、実際に停止したかを確かめます。

確認間隔を長くすると、完了に気づくのが遅くなる場合があります。効果はスキルの選択と指示への追従にも左右されます。モデル呼び出しの削減、外部サービスへの確認回数、結果の通知速度は別々に評価する必要があります。

## 導入と使い方

1. このディレクトリ全体を `${CODEX_HOME:-$HOME/.codex}/skills/codex-wait-efficiently/` にコピーします。`CODEX_HOME` を設定していない場合は `~/.codex/skills/codex-wait-efficiently/` です。更新時は以前の同名スキルを置き換えます。
2. 新しい Codex セッションを開始します。自動選択は標準で有効です。明示的に使わせたい場合は、依頼に次の一文を加えます。

   ```text
   このジョブの完了待ちには $codex-wait-efficiently を使ってください。
   ```

3. このリポジトリの AGENTS.md パッチから切り替える場合は、指示の重複を避けるため、グローバル AGENTS.md の該当する `## Waiting for work` セクションを削除します。ほかの指示は残してください。

通常の利用に補助スクリプトや別のスキルは必要ありません。ランタイム評価では `sleep_tool` をデフォルト設定のまま使用しました。`clock.sleep` は利用可能かつ適切な場合に使います。この README と `evals/` は説明・評価用の資料であり、`SKILL.md` は通常の待機でこれらを読み込むようには指示していません。

## スキルなしとの直接比較

2026 年 9 月 15 日に、Codex CLI 0.154.0、GPT-6 Astra、推論強度 low で **18 試行**を新たに実行しました。各条件で、75 秒のコマンド、実際のサブエージェント、ローカルの CI シミュレーターをそれぞれ 3 回測定しています。タスクの依頼文は両条件で同一です。スキルありの条件では最終版 v4 だけを有効にして自動選択させ、スキルなしの条件ではすべてのスキルを無効にしました。両条件とも AGENTS.md パッチはなく、バンドル済みスキルと無関係な共有スキルも無効です。

| 指標 | スキルなし | 最終版 v4 |
| --- | ---: | ---: |
| モデル応答数 | 100 | 64 |
| 入力トークン合計 | 1,547,548 | 1,028,592 |
| 通常入力 | 106,396 | 76,784 |
| キャッシュ読み込み | 1,441,152 | 951,808 |
| 記録されたキャッシュ書き込み | 0 | 0 |
| 出力トークン | 4,000 | 4,599 |
| API 単価による換算額 | $2.705112 | $1.949598 |

次の表は、対象ごとに各条件 3 試行分を集計したものです。遅延はジョブの完了から最終回答までの平均時間です。

| 対象 | 応答数：なし → v4 | API 換算額：なし → v4 | 平均遅延：なし → v4 |
| --- | ---: | ---: | ---: |
| コマンド | 27 → 13 | $0.680330 → $0.408696 | 3.589 s → 3.839 s |
| サブエージェント | 49 → 30 | $1.428170 → $0.867522 | 4.420 s → 12.239 s |
| CI | 24 → 21 | $0.596612 → $0.673380 | 5.805 s → 31.073 s |

18 試行すべてで正しい結果を返しました。スキルありでは、親 9 試行と子 3 試行すべてでスキルを読み込み、9 試行すべてが自動判定に合格しました。1 秒指定の `write_stdin` は 39 回からゼロになりました。対応する 9 組のうち、8 組で応答数と入力トークンが減り、7 組で換算額が下がりました。

**CI 単独では換算額と通知までの時間が増えました。** 実際の状態確認は両条件とも計 12 回でした。スキルありでは、通常入力と出力の増加分がキャッシュ読み込みの減少分を上回り、換算額が 12.87% 増えました。2 試行では確認間隔を 15・30・60 秒と延ばしたため、対応するスキルなしの試行より約 37〜39 秒遅く結果を通知しました。また、3 試行すべてで監視開始時に 1 秒の待機を指定し、2 試行で Code Mode のセル再開が追加で必要になりました。自動判定は指示への追従をすべて網羅しているわけではありません。

結果を届けるまでの時間は 9 組中 8 組で延びました。上の表はジョブ完了後の平均遅延を示しており、最初のスキル読み込みなど、ジョブ開始前の時間は含みません。今回の節約効果を主に支えているのは、コマンドとサブエージェントの待機です。

数値には親・子エージェントの推論、スキルの読み込み、不合格の項目があった試行も含めています。入力合計はキャッシュ読み込みと記録された書き込みを含みます。金額は調査で用いた 2026 年 9 月 14 日時点の Standard API 単価による換算値であり、実際のサブスクリプション請求額や利用枠の節約率は未測定です。書き込みがゼロでも、上流の利用量報告に項目がなかった可能性が残ります。

試行順を混在させた小規模な Astra・模擬 CI の測定であり、キャッシュ状態は制御していません。Sol、本番 CI、長時間のキャッシュ保持、`/goal` の一時停止、多数のスキルがある環境での選択は未検証です。方法と集計の詳細は[直接比較レポート](../../docs/reports/CODEX_WAITING_SKILL_VS_NO_SKILL_BENCHMARK.md)に記載しています。

## 先行評価と改善内容

先行評価では、4 つのスキル版と追加確認を合わせて **66 試行**を実際の Astra/low で実行しました。明示指定と自動選択、スキルを使わない依頼、実際の子エージェント、コマンド失敗、観測上限、独立作業、Code Mode のセル再開を評価し、すべての依頼で正しい結果を返しました。

V4 は元のスキルに 31 語を追加し、CI 監視の上限とまとめ方、待機を含む委任時のスキル使用依頼を明確にしました。最終版の子エージェントを使う 3 試行では、いずれも子がスキルを読み込み、短いポーリングを避けられました。全ケースの評価と 2 回の追加確認では、**14/14 試行で結果が正しく、13/14 試行がすべての自動判定項目に合格**しました。残る CI の 1 試行では 1 秒のセル待機が発生しました。

初版と最終版の同じ 12 ケースでは、応答数は **57 対 58**、API 換算額は **$1.856236 対 $1.945212** でした。この結果からは改訂自体による節約効果を確認できませんでした。上記の新しい比較は、最終版を導入する効果をスキルなしと比べたものです。各候補と不合格の内容は[先行評価レポート](../../docs/reports/CODEX_WAITING_SKILL_EVALUATION.md)に記録しています。

## AGENTS.md パッチとの関係

このスキルは[最終版の AGENTS.md パッチ](../../docs/guides/AGENTS.waiting-compatible.md)をもとに作成しました。今回の測定では、スキルの削減率は AGENTS.md パッチよりも小さくなりました。以下は、各実験でそれぞれの未適用条件に対して得られた削減率です。どちらも CLI 0.154.0、Astra/low で 18 試行を実施しています。

| 削減した指標 | AGENTS.md パッチ | 最終版スキル v4 |
| --- | ---: | ---: |
| モデル応答数 | 52.04% | 36.00% |
| 入力トークン（キャッシュを含む） | 51.03% | 33.53% |
| API 単価による換算額 | 42.31% | 27.93% |

スキルの実験では、コマンドとサブエージェントの換算額がそれぞれ 39.93%、39.26% 減る一方、CI は 12.87% 増えたため、全体の削減率が小さくなっています。ただし、この内訳だけでは、二つの実験の差が何によるものかは特定できません。

[AGENTS.md の実験](../../docs/reports/CODEX_WAITING_LATEST_VS_NO_PATCH_BENCHMARK.md)と[スキルの実験](../../docs/reports/CODEX_WAITING_SKILL_VS_NO_SKILL_BENCHMARK.md)では、依頼文と指示の読み込み条件が異なり、キャッシュ状態やバックエンドの実行順序も制御していません。「今回のスキル実験では削減率が小さかった」とは言えますが、導入形式そのものが効率に与える影響を判断するには、条件をそろえた直接比較が必要です。
