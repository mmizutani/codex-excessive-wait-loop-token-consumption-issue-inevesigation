# AGENTS.md の pragma 指定を省いた文面のランタイム再測定

## TL;DR

**現在の構文省略版は、CLI 0.154.0／Astra・low の6試験すべてで正常に動きました。ただし、直前の構文あり版と同じトークン効率を維持することは確認できませんでした。**

- 3文面×3対象×2反復の計18試験を新規実行し、全件が完了・回答形式・使用量照合などの受入条件を満たしました。外側の早期復帰と `functions.wait` によるセル再開は全18件で0回です。
- **直前の構文あり版から省略版への変更（B→C）では、応答29→33回（+13.79%）、入力458,288→522,123トークン（+13.93%）でした。** API単価換算額は $1.110416→$1.086094（−2.19%）でしたが、キャッシュ読み出しの割合が上がった影響を含みます。
- 測定済み旧版と現在の省略版（A→C）を新規実行で比較すると、応答31→33回（+6.45%）、入力489,469→522,123（+6.67%）、API単価換算額 $1.042454→$1.086094（+4.19%）でした。
- 差は主に内側の待機時間とCI監視の区切りに現れました。省略版は継続待機に40秒を選び、通常コマンド1件と子エージェント2件で完了直前に待機が切れました。pragma を生成できず外側が早く返る問題は観測していません。
- 現在の配布文面を維持します。**実装構文をプロンプトに重複させないという方針で使える文面ですが、使用量が変わらない、または最も安い文面として推奨できる結果ではありません。** 将来のランタイムでも同じ効果が続くことは未検証です。
- パッチ全体が過剰なモデル呼び出しを抑えるという評価は、従来版の導入比較と、最新文面で観測した待機動作から支持されます。ただし、今回の18試験にはパッチなしの条件がなく、最新文面そのものの導入効果や削減率を直接測った結果ではありません。

## 比較条件と集計方法

2026年9月15日（日本時間）に、インストール済みの公式 Codex CLI 0.154.0 と実際のサブスクリプション認証で測定しました。Astra／low、共有・同梱スキルの指示を無効化し、各試験に新しい一時 CODEX_HOME と作業ディレクトリを使いました。モデルカタログは以前の比較と同じものを固定し、旧版の対照試験もすべて新規に実行しています。

| 条件 | 文面 | 比較の役割 |
| --- | --- | --- |
| A：測定済み旧版 | `outer-o0n0` と完全一致。外側のツール名は暗黙、先頭行の pragma を明記 | 修正全体に対する新規対照 |
| B：明確化・構文あり | 外側・内側のツール名とセル再開を明記し、pragma の指定も残す | 構文への言及を削除する直前の文面 |
| C：明確化・構文なし | 現在の配布版と完全一致。待機対象と時間の関係を示し、pragma の構文を省く | 今回再測定する文面 |

BとCで異なるのは、Code Mode の段落の第1文だけです。ただし、Cには “long enough to cover” などの書き換えも含まれます。この実験が測るのは配布する文章どうしの差であり、`@exec` という文字列だけの因果効果には分解できません。

コマンド・CI・サブエージェントの3対象を、3文面で各2回、計18試験実行しました。各反復内の9件を固定シードで並べ替え、最大2件を同時実行し、その反復が終わってから次の反復へ進めました。実際のコマンドと子エージェントを使い、モデル応答のモックは使っていません。CIだけはローカルの状態シミュレーターです。処理時間はいずれも75秒です。

サブエージェントは、親の Astra／low を継承する `fork_turns: "all"` を共通タスクに明記し、モデル・推論設定の上書き引数を省かせました。過去に起きたタスク文の解釈による不要な確認を避けるためです。

親・子の応答IDを重複排除し、応答ごとの使用量をセッションの累計カウンターと照合しました。入力合計は通常入力・キャッシュ読み出し・記録された書き込みを含み、出力には推論トークンを含みます。入力合計を区分別入力に重ねて課金する計算はしていません。

金額は、比較可能性を保つため従来と同じ2026年9月14日の Standard API 単価で換算しています。100万トークン当たり、通常入力 $10、キャッシュ読み出し $1、書き込み $12.50、出力 $50 です。長文入力の倍率は応答ごとに判定します。現在の単価を再取得したものでも、サブスクリプションの請求額でもありません。記録上の書き込み0には、上流で未報告だった場合も含まれ得ます。[従来の単価・計算方法](CODEX_WAITING_RUNTIME_PROMPT_BENCHMARK.md#token-categories-and-api-price-dollars)

正しい結果、終了コード0、単一起動、子の数、実際のモデル・推論設定、fork設定、スキル未使用、待機引数、実行中セルの返却、親の報告間隔、結果通知の遅延も確認しました。待機引数は完全な呼び出し文を確認し、数字の抽出結果だけで判断していません。

## 実際の待機から分かったこと

### 構文を省いても、外側の待機設定は生成された

Cの通常コマンドと子エージェントでは、初回の内側30秒に対して外側35秒、継続待機の内側40秒に対して外側45秒を設定しました。AGENTS.md に pragma の書き方がなくても、有効な pragma を使っていました。設定対象と時間の関係を残す文面で、今回のランタイムでは処理を完了できています。

ただし、CのCI第1試験では、最初の状態取得と監視コマンドの起動で外側の設定が省略されました。特に後者は、内側30秒・外側は既定の30秒のままで、記録上は約30.2秒後にセルが完了しました。すべての呼び出しでモデルが明示的な余裕を設定した、と評価することはできません。

v0.154.0 のソースを確認すると、Code Mode は10秒以上の yield に1秒の猶予を加え、その後にセッションの上限で制限します。既定30秒で約30.2秒の処理を収めた観測は、この実装と整合します。モデルがこの猶予を意識していたかは分かりません。この猶予で内側40秒を収められるわけではなく、継続待機では外側の調整が必要です。[リリースの実装](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/code-mode-runtime/src/service.rs#L192-L207)、[既定値とソースの記録](waiting-benchmark/numeric-waits/wording-runtime-evidence.json)

### 追加応答は内側の待機終了で発生した

Cは通常コマンド・子エージェントの4件すべてで、継続待機に40秒を選びました。Bの対応する4件はすべて44秒です。Cの通常コマンド第1試験では、40秒の待機がジョブ完了の約1.185秒前に返りました。子エージェントの2件は、それぞれ約1.494秒前と0.408秒前に返っています。3件とも、次の `write_stdin` はすでに完了した結果をほぼ即座に受け取りました。

Cの通常コマンド第2試験は同じ40秒でも追加待機なしで完了しています。Aの子エージェント第1試験にも、40秒の待機が約0.909秒前に返る例がありました。75秒のジョブでは、30秒＋40秒の待機に通信・モデルの応答時間を加えた長さが完了境界に近く、わずかな時間差で追加応答の有無が変わります。

この結果は、文面による内側の時間選択の差を示します。構文の省略そのものが原因なのか、“long enough to cover” などの表現が時間選択を変えたのかは、この比較だけでは切り分けられません。外側が先に返って `functions.wait` を呼ぶ問題は全件で発生していません。[引数と返却時刻](waiting-benchmark/numeric-waits/wording-results/behavior.json)

### CIは監視スクリプトの間隔にも左右される

実際のCI状態取得は、Aで計10回、Bで8回、Cで10回でした。CのCI第2試験は、Bの対応する試験よりモデル応答が1回多くなりました。初回に30秒、その後に40秒待つ点は同じでも、生成した監視スクリプトの確認時刻が異なります。Bは開始約82.0秒後、Cは約101.9秒後に完了を検出しました。

そのため、CIの差を外側の待機だけに帰属させることはできません。処理開始から状態取得までの遅れやバックオフの選択も結果に含まれます。CはAより平均通知遅延が短く、Bより長い結果で、全指標で一方が優れているわけではありません。

## 現在の推奨文面と判断

パッチ全体の有効性と、今回の文面修正による効率差は別の比較です。以前のパッチなし／旧コンパクト版の比較では、Astraのモデル応答が36→16回に減りました。最新文面でも、長いツール待機、同じプロセスの継続、CI監視スクリプトによる待機が機能しています。この組み合わせは、最新文面も過剰なモデル主導の確認を抑えるという推論を支持します。[従来版の導入比較](CODEX_WAITING_RUNTIME_PROMPT_BENCHMARK.md#final-compact-patch-astra-only-shared-skills-disabled)

一方、今回の18試験はすべてパッチありの条件です。最新文面とパッチなしを直接比較しておらず、過去の試験とは測定時点も異なるため、両者の数値をつないで最新文面の削減率を算出することはできません。社内向けには「Astra／CLI 0.154.0 で過剰な待機確認を抑える対策として有用と考えられる。効果は作業と実行条件で変わり、最新文面の削減率は未確定」と説明するのが適切です。

今回測定したCと配布ファイルは完全一致しています。第1文は次のとおりです。

> In Code Mode, set the outer `functions.exec` wait long enough to cover the inner `exec_command` or `write_stdin` wait plus a small margin, while staying within budget.

実装構文を AGENTS.md に重複させないという利用者の方針に沿い、この文面を維持します。処理の正常完了、同じジョブの継続、不要なセル再開の回避は今回確認できました。一方、Bより応答数と入力合計が多かったため、「構文を省いても使用量への影響はない」という説明には修正が必要です。効率だけを優先するなら、今回の応答数と入力合計はBが最少でした。

将来のランタイムに対する保守性は、今回の単一バージョンの実験で証明できる性質ではありません。今後設定構文が変わった場合のモデルの追従も未検証です。今回の観測に合わせて別の文面を探し続ける追加試験や、個別の秒数指定の復活は行っていません。

## 全試験の使用量と検証範囲

全18試験で93応答、入力1,469,880トークン（通常158,776、キャッシュ読み出し1,311,104、記録上の書き込み0）、出力6,802トークン（うち推論336）でした。API単価換算額は、通常入力 $1.587760、キャッシュ読み出し $1.311104、書き込み $0、出力 $0.340100、合計 **$3.238964** です。調査・報告作成用の親エージェントの使用量は含みません。

全件で受入確認と応答ごと・セッション累計の照合を通過しました。親の報告間隔の最大値は全体で53.847秒、Cで49.012秒でした。全試験で60秒以内です。過去の試験、失敗記録、文面のハッシュは変更していません。

- 対象ごと各条件2回の短時間測定であり、統計的な同等性や普遍的な最適性は主張できません。
- キャッシュ状態は固定していません。金額の順位は応答数・入力合計の順位と一致しません。
- 自然な待機だけを測定し、実行中セルを強制発生させていません。全件でセルが直接完了したため、現在の文面による `functions.wait` の呼び分けは今回の実行では試されていません。
- CIはローカルのシミュレーターです。実サービスの通知連携や障害処理、30分のキャッシュTTL境界、長期の `/goal` 待機、Sol、別の推論設定は対象外です。
