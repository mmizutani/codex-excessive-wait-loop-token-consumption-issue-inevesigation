# Codex の待機ルール：各指示の理由と期待する効果

Codex はデフォルト設定のままでは、サブエージェント、長時間コマンド、CI などの外部処理の進捗確認を過剰な頻度で繰り返すことがあります。エージェントが確認結果を読み、次の確認や待機を判断するたびに、**モデルへの API 呼び出しが発生し、状態に変化がなくても入力・出力トークンが消費されます。** この反復が、待機中のトークン消費とコストを不必要に膨らませます。

この文書で解説する AGENTS.md への推奨パッチは、**完了待ちや進捗確認をツール・監視スクリプト側で処理し、モデルによる判断が不要な間の API 呼び出しを減らす**ための追加指示です。待機手段と待機時間を指定して過剰な確認を抑え、必要な進捗報告、完了後の結果処理、検証を維持します。

対象は、2026年9月14日の追加測定を踏まえた [AGENTS.waiting-compatible.md](AGENTS.waiting-compatible.md) です。初回の `exec_command` と外側の `functions.exec` の秒数指定を省き、待機時間を選ぶ条件を残した版です。末尾にパッチ全文を掲載しています。適用時は、コードブロック内の英語指示だけをコピーしてください。

## TL;DR

- 対象は、サブエージェント・コマンド・外部状態の確認で、**モデルへの API 呼び出しが過剰に繰り返される問題**です。確認のたびにモデルへ戻る回数を減らし、待機中のトークン消費とコストを抑えます。
- モデルが短い間隔で状態を問い合わせる方法より、`wait_agent` や `write_stdin` で通知・出力・終了を待つ方法を優先します。CI などで完了通知を利用できなければ、可能な範囲で監視スクリプトに状態確認をまとめます。
- これらの待機ツールを **Code Mode**（JavaScript 経由でツールを呼ぶ方式）で使う場合は、内側のツールが待機中なのに、外側の JavaScript 実行が先にモデルへ制御を返すことがあります。その余分な API 呼び出しも抑えるため、内外の待機時間を調整します。
- 検証対象の Codex には「作業中、進捗報告の間隔を60秒より長く空けない」という組み込み指示があります。1回の待機を45秒以内にして前後の処理と報告生成に余裕を設けますが、通信や応答の遅延によってはさらに短縮する必要があります。
- 長く待てば必ず安くなるわけではありません。確認間隔を延ばすと結果の通知が遅れることがあり、キャッシュ維持だけのアクセスにもコストがかかります。
- 旧コンパクト版を GPT-6 Astra モデルで試した短時間の比較では、入力トークンが **54.64%**、API 単価による換算額が **46.55%** 減りました。ただし CI の結果通知は導入前より約16秒遅くなりました。現在の文面への修正前の結果で、契約料金やすべての業務での削減を保証するものではありません。
- 追加測定を踏まえ、ツールごとの固定秒数を省き、外側の `functions.exec`、内側の `exec_command`／`write_stdin`、実行中セルを待つ `functions.wait` の関係を明記しました。さらに設定構文を省いた現在の文面を再測定し、6試験すべてが完了・使用量照合などの条件を満たしました。ただし、直前の構文あり版に対して応答は29→33回、入力は13.93%増えています。共通の45秒上限と待機時間の関係は維持していますが、同じ使用量で動くことを確認した結果ではありません。[現在の文面の再測定](../CODEX_WAITING_PRAGMA_REMOVAL_BENCHMARK.md)
- 従来版の導入比較と現在の待機動作から、過剰なモデル主導の確認を抑える対策として引き続き有用と考えられます。ただし、最新文面とパッチなしを直接比較した測定はなく、最新文面の削減率は未確定です。

## なぜ「待つだけ」で使用量が増えるのか

ツールの内部で待っている間や、監視スクリプトが状態取得を繰り返している間は、その処理のためにモデルへの API 呼び出しは発生しません。モデルへの呼び出しが増えるのは、ツールが短時間で制御を返し、その都度モデルが次の確認や待機を判断する場合です。

たとえば、ツールから「まだ実行中」という結果が返るたびに、モデルが状況を読み、次の確認を指示すると、情報がほとんど増えていなくても新たな推論が発生します。ネットワーク上の転送量にかかわらず、その時点で保持されている会話履歴や指示も入力トークンとして計上されます。キャッシュが使えても、読み出しや新規入力・出力にはコストがかかります。

パッチは、この反復を減らすようにツールの使い方を指定します。モデルが書いた監視スクリプトの内部で状態を確認することと、確認のたびにモデルへ戻ることは区別します。また、親エージェントが効率よく待っていても、子エージェントが細かい確認を繰り返せば、全体の使用量は増えます。

以降の「モデル応答回数」は、このモデルへの API 呼び出しに対する応答の回数です。ユーザーの1つの依頼に対しても、ツールの呼び出しと結果の受け取りを挟んで複数回発生します。全体の使用量は、親エージェントとサブエージェントを合算して評価します。

パッチがモデルに使い分けを指示するツールは、次のとおりです。

| ツール・機構 | 役割 |
| --- | --- |
| `wait_agent` | 別のエージェントからの完了通知やメッセージを待ちます。 |
| `exec_command` / `write_stdin` | シェルコマンドを起動し、その同じ実行の出力や終了を待ちます。 |
| Code Mode の `functions.exec` / `functions.wait` | モデルが書いた JavaScript からツールをまとめて呼ぶ機構です。`exec` が JavaScript を実行し、まだ終わっていない実行の続きを `wait` で受け取ります。 |
| `clock.sleep` | Codex に指定時間の待機を依頼するタイマー型のツールです。次の確認まで間隔を空けるときに使い、CI やコマンドの完了状態そのものは調べません。 |

`clock.sleep` は通常、指定時間が経過すると戻ります。利用者からの新しい入力で早く戻る場合はありますが、CI の完了だけでは待機を解除しません。完了を検知できる待機ツールを優先すると、結果をより早く処理できます。

## 適用方法

末尾の英語パッチを、グローバルな `${CODEX_HOME:-$HOME/.codex}/AGENTS.md` に追加します。`CODEX_HOME` が未設定なら、通常は `~/.codex/AGENTS.md` です。同じ `CODEX_HOME` を使う全プロジェクトに適用されます。

既存の指示は残し、以前の待機ルールがあれば同じ節を置き換えます。追記後は新しいセッションを開始し、指示を読み込ませます。日本語の解説は利用者向けの資料として保管してください。スキルの導入は不要です。

以下はパッチの各節に対応しています。「期待する効果」は設計意図を示します。待機時間の具体値については、追加比較の実測結果も示します。すべての指示を1つずつ切り分けて効果を測ったわけではありません。

## 1. Across all waits：すべての待機に共通する指示

### Codex に組み込まれている「60秒以内の進捗報告」に従う

**60秒は Codex 側の上位指示で決まっており、通常の AGENTS.md への追記では変更できません。** 検証した CLI 0.154.0 の Astra 用モデルカタログには、`model_messages.instructions_template` という基礎指示のテンプレートがあり、その中に次の指示が実際に含まれています。

> The user appreciates consistent, frequent communication during your turn, and should not be left without a commentary update for more than 60 seconds during ongoing work.

作業中は、利用者向けの途中経過メッセージである `commentary` の間隔を、60秒より長く空けない、という指示です。加えて、次の指示もあります。

> Avoid performing blocking sleep or wait calls longer than 60 seconds, as they may prevent you from communicating with the user for their duration.

待機ツールの実行中はモデルが報告を書けないため、60秒を超えるブロッキング待機を避ける、という内容です。どちらも測定した環境に含まれていた組み込み指示です。[CLI 0.154.0 の公開モデルカタログ](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/models-manager/models.json)

公開実装では、この基礎指示を `developer` ロールでモデルへ渡しています。AGENTS.md より優先度が高いため、「報告は5分ごとでよい」と追記しても上書きできません。[基礎指示を developer として扱う実装](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/context/base_instructions.rs#L12-L14)

### 60秒の報告間隔が求められる理由

この60秒は、利用者への進捗報告の間隔です。利用者が作業の継続・入力待ち・停止を判断できるように、長時間報告が途切れることを避ける目的があります。

CI やコマンド自体は60秒を超えて実行でき、ツールが60秒を超える待機を受け付ける場合もあります。ただし、報告間隔が60秒を超えると、処理が正常に続いていても上記の組み込み指示に反します。

### 利用者が60秒を変更する方法はあるのか

調査した CLI 0.154.0 の設定定義には、この進捗報告間隔だけを変更する専用項目は見当たりません。コマンドやエージェントの待機時間を長く設定しても、モデルに渡される「60秒以内に報告する」という文章は変わりません。

`model_instructions_file` を使うと、対象モデルの基礎指示全体をファイルから差し替えられます。変更の影響は報告間隔以外にも及びます。ソースコードの説明でも、Codex が用意した指示から外れて性能が低下するおそれを理由に、利用を強く非推奨としています。別途付加される上位指示は引き続き有効です。[設定の定義と注意書き](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/config/src/config_toml.rs#L249-L253)

今回の提案では、変更範囲を小さく保ち、既存の応答性を維持するため、基礎指示を差し替えずに60秒の報告要件へ合わせます。**既存の上位指示との共存を重視した推奨**です。報告頻度を下げれば使用量が減る可能性もありますが、その構成との比較は未実施です。用途ごとの最適な報告間隔や、最も安くなる間隔は未検証です。

### 必要な独立作業は、待機に入る前に進める

待っている結果に依存しない必要な作業があれば、先に進めます。たとえばテストの完了を待つ間に、依頼の範囲内で変更箇所をレビューできます。結果が必要になるまで他の作業を進めることで、待機だけを目的としたやり取りを減らせます。

### 必要な進捗報告は、待機ツールを呼ぶ同じ応答に含める

残っている作業が待機だけで、進捗報告が必要なら、「完了通知はまだ届いていません。引き続き待ちます」など、把握している情報だけを短く報告し、同じモデル応答で待機ツールを呼びます。

これにより、報告と次の待機を1回のモデル応答にまとめられます。報告は上位指示で必要な場合に行います。そのためのモデル呼び出しと、報告文の出力トークンは引き続き発生します。

### 60秒ごとの報告が必要なら、待機とラッパーの上限を45秒にする

前回の報告から次の報告までは、ツールで待つ時間に加えて、ツールの呼び出し、通信、結果を受け取ったモデルの応答生成にも時間がかかります。ツールだけで60秒待つと、これらの時間の分だけ、利用者への報告間隔が60秒を超えます。

たとえば、報告後に待機を開始するまで5秒、待機後に次の報告を生成するまで5秒かかった場合、60秒の待機では報告間隔が70秒、45秒の待機なら55秒です。この5秒ずつは仕組みを示す例で、測定値ではありません。45秒という上限は、60秒の中に前後の処理の余裕を約15秒確保するために設けています。

これは遅延の上限保証ではありません。前後の処理に15秒以上かかる場合や、ツールの制限、次に対応すべき期限がある場合は、さらに短くする必要があります。基礎指示により報告間隔が異なる環境でも、その間隔に合わせて調整します。

**指定する時間は待機の上限です。** 完了や通知を検知できるツールなら、それを受けて早く戻れる場合があります。`clock.sleep` のような時間待ちとの違いは、後述します。

### 進捗報告のためだけに、状態確認を追加しない

「ユーザーへ報告する時刻になった」ことと、「外部の状態を再確認する必要がある」ことは別です。すでにコマンドや監視処理を動かしていて新しい結果を受け取っていなければ、最後に確認した状態や、完了通知がまだ届いていないことを報告できます。

報告のたびにエージェント一覧、コマンド状態、CI の状態を追加取得すると、情報が変わっていなくてもツール呼び出しやモデル応答が増えます。この指示は、その追加確認を抑えます。報告には、確認済みの情報と確認時点を正しく反映します。

### キャッシュ維持だけのアクセスは、節約効果を測るまで追加しない

プロンプトキャッシュは、以前のモデル呼び出しと共通する入力部分の計算結果などを再利用する仕組みです。読み出しが使えると入力処理の負担や API 単価を抑えられますが、保存期間を過ぎるなどして再利用できなければ、同じ入力でもコストが変わる場合があります。

確認回数を減らせば入力トークンの計上を抑えられますが、長い間隔を空けた後のキャッシュ状態によっては、次の応答コストが変わる場合があります。しかし、キャッシュを維持するためだけにモデルを呼び出しても、キャッシュ読み出し、新規入力、出力の各コストが発生します。

仮に「30分」をキャッシュ寿命の前提にしても、それだけで「25分ごとに維持アクセスを入れると安い」とは判断できません。この調査では、Codex サブスクリプションにおける30分の保証や、期限をまたぐ待機のコストを独立に確認していません。

そのため、パッチはキャッシュを無視せず、同時に未測定の維持アクセスも勧めません。60秒ごとの進捗報告などで通常のモデル呼び出しが続いている場合は、その活動とは別にキャッシュ維持ループを追加する理由もありません。

## 2. Subagent results：サブエージェントの結果を待つ

独立した作業を終え、残りがサブエージェントの結果だけなら、直接 `wait_agent` を使います。これはエージェントからの通知やメッセージを待つ仕組みです。短い間隔で状態一覧を取得し続けるより、モデルが判断し直す回数を減らすことを狙っています。

`timeout_ms` は、共通ルールの待機時間の範囲に収めます。60秒ごとの報告が必要な環境では、たとえば `45000` です。通知やメッセージで待機が早く終わる場合もありますが、届いた内容がタスク完了を意味するかは別途判断します。

タイムアウトは「指定した観測時間が終わった」という意味です。それだけで子エージェントの失敗や停止を判断したり、同じ作業を別の子にやり直させたりしません。通知がない場合でも、子の作業は続いている可能性があるためです。

## 3. Terminal commands：長時間コマンドを待つ

### 共通ルールだけにせず、この節を残す理由

共通ルールの「待機は45秒以内」は上限の指定です。それだけでは、長時間コマンドを1秒でいったん返し、短い予備確認を挟む待ち方も許す形になります。この節では、初回から長めの待機を使うこと、同じ実行セッションを使い続けること、Code Mode の内側と外側の待機を合わせることを補います。CIの監視スクリプトや、子エージェントが実行するコマンドにも適用します。

節全体の有無を比較した追加12試験では、削除版で短い予備確認が再発しました。親子合計のモデル応答は33→36回、入力トークンは8.49%、API単価換算額は5.19%増えています。内訳は、CIが9→11回、コマンドが8→9回、サブエージェントが16→16回でした。

一方、削除版の結果通知は各対象で平均約4〜14秒速く、両条件とも60秒以内の報告間隔を守りました。この節の削除比較は、秒数を明記した旧コンパクト版を基準としています。不要なモデル呼び出しを抑える指示は残し、その後の個別比較に基づいて秒数の重複指定を省きました。各条件2試験の結果から、節内のすべての文が不可欠とは言えません。[節削除の比較と実際の呼び出し](../CODEX_WAITING_NUMERIC_OVERRIDES_BENCHMARK.md#terminal-commands-節全体を削除する比較)

### 最初から適切な長さで待ち、同じ実行セッションを使い続ける

残りがコマンドの完了だけなら、`exec_command` の初回から、ツールの上限と報告期限に収まる長い `yield_time_ms` を選びます。CLI 0.154.0 の初回上限は30秒です。共通ルールが45秒以内でも、ツール固有の上限が短ければ、そちらに合わせます。報告の期限が近ければ、さらに短縮します。追加測定では30秒を明記しなくても30秒が選ばれたため、現在のパッチには `30000` を固定値として書いていません。[コマンド起動時の待機上限](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/unified_exec/mod.rs#L75-L78)

最初に短時間で戻り、直後に「まだ実行中か」を再確認する流れを避けるための指示です。コマンドが選んだ待機時間より早く終われば、その結果を受け取ります。まだ実行中なら、`exec_command` が返すセッション ID を保持し、次の待機には `write_stdin` を使います。`write_stdin` にその ID を渡すことで、起動済みの同じプロセスを引き続き待てます。

継続待機では、`write_stdin` の `chars` を空文字列 `""` にします。入力を送らずに、既存のプロセスの出力や終了を待つ使い方です。初回の直後に予備的な短い確認を挟まず、必要な長さの待機に進みます。これにより、余分なモデル応答とコマンドの重複実行を避けます。

### Code Mode では「内側」と「外側」の待機時間を合わせる

Code Mode は、Codex がツールの呼び出しや結果処理を JavaScript にまとめて実行する方式です。待機ツールをこの方式で呼ぶと、ツール自体に加えて、それを呼び出す JavaScript の実行を待つ必要が生じます。

**内側のツールは、初回が `exec_command`、2回目以降が `write_stdin` です。外側は、どちらも `functions.exec` です。** 初回の JavaScript が完了してモデルへ結果を返した後、コマンドがまだ実行中なら、新しい `functions.exec` の中から `write_stdin` を呼びます。

`functions.exec` が JavaScript の実行中セルを返した場合は、`functions.wait` にそのセル ID を渡して続きを待ちます。`functions.wait` が待つ対象は、この外側のセルです。セル内の `exec_command` や `write_stdin` の呼び出しは継続しているため、まずセルの結果を受け取り、コマンドがまだ実行中なら次の `write_stdin` に進みます。

以下は待機の構造を示す実測例です。初回30秒・外側45秒・継続40秒は、現在のパッチが固定値として要求するものではありません。初回の外側を31秒や35秒、継続の内側を44秒とした実行もありました。

```text
初回：コマンドを起動し、最初の結果を待つ
モデル
  └─ functions.exec〔外側：45秒〕
       └─ exec_command〔内側：30秒〕
            └─ コマンドを起動

コマンドがまだ実行中なら、セッション ID を受け取って次へ

2回目以降：同じコマンドの出力・終了を待つ
モデル
  └─ 新しい functions.exec〔外側：45秒〕
       └─ write_stdin〔内側：40秒、同じセッション ID、空入力〕
            └─ 起動済みのコマンドを引き続き待つ

各回の JavaScript 自体がまだ実行中なら、functions.wait でその結果を待つ
```

各ツールは指定した待機時間に達すると制御を返し、実行中のコマンドはその後も継続します。内側に指定できる待機時間の上限は、ツールごとに異なります。

| 段階 | 内側のツール | 実装が受け付ける1回の待機時間の上限 | 実測例の指定：内側／外側 |
| --- | --- | --- | --- |
| 初回 | `exec_command` | 30,000 ms（30秒） | 30,000 ms／45,000 ms |
| 2回目以降 | 空入力の `write_stdin` | 既定設定で300,000 ms（300秒） | 40,000 ms／45,000 ms |

空入力の `write_stdin` の上限は、CLI 0.154.0 の `background_terminal_max_timeout` で設定され、既定値は300秒です。初回の `exec_command` に適用される30秒の上限とは別に管理されています。[継続待機の上限設定](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/config/mod.rs#L1042-L1044)、[空入力時の上限適用](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/unified_exec/process_manager.rs#L952-L960)

ただし、このパッチでは60秒以内の進捗報告に合わせて、外側の待機を45秒以内に収めます。内側の `write_stdin` もその枠に収めるため、実測例では40秒にし、ラッパーの処理に約5秒の余裕を残しています。**実装上は300秒まで指定できても、この報告要件の下では短く設定する必要があります。**

外側の45秒の待機枠に、内側の40秒の待機が含まれます。内側を待っている間も外側の時間は経過するため、合計85秒待つ指定ではありません。

この指示は、実際に Code Mode 経由でツールを使う場合に適用します。ツールを直接呼ぶ経路には外側の JavaScript 実行がないため、追加のラッパー待機も不要です。

### 既定値に任せず、待機の条件を指定する理由

CLI 0.154.0 の既定値では、長時間の待機中にモデルへ制御が戻る回数が多くなる場合があります。現在のパッチは、各ツールの秒数を固定せず、十分な待機時間を報告期限内で選ぶ条件を指定します。秒数を省くことは、引数を省略して既定値を使わせることではありません。表の時間は、呼び出しが制御を返すまでの待機時間（`yield_time_ms`）です。その時間に達した後も、実行中のコマンドは継続します。

| 設定 | 検証した CLI 0.154.0 の既定値 | パッチが求める条件（秒数は実測例） | 採用理由 |
| --- | --- | --- | --- |
| 初回の `exec_command` の待機時間 | 10,000 ms（10秒） | ツールの上限と報告期限に収まる長い待機。実測では30秒 | 30秒の明記による追加効果が見られず、長さを選ぶ条件だけを残した。 |
| 外側の `functions.exec` の待機時間 | 30,000 ms（30秒） | 内側の待機と少しの処理時間を収め、報告期限内に戻るよう設定 | 共通の45秒上限から選べており、重複する45秒指定の利点を反復して確認できなかった。現在のパッチでは、外側と内側のツール名、および待機時間の関係を明記し、設定構文は実行時のツール定義に委ねる。 |
| 継続待機の空入力 `write_stdin` | 省略時は実効5,000 ms（5秒）。一般の入力送信時の既定値250 msに、空入力用の下限5秒が適用される | 数値を固定せず、外側の待機枠と処理の余裕に合わせる。40秒は実測例 | 追加比較で40秒の明示による削減が見られず、現行の指示を維持した。 |
| 実行中セルを再開する `functions.wait` | 10,000 ms（10秒） | 数値を固定せず、待機枠内で1秒刻みや既定値のままの確認を避ける | 追加比較では、明示しなくても45秒を1回だけ呼んでセルを受け取れた。 |

初回の10秒という既定値と30秒の上限は、[コマンドハンドラー](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/handlers/unified_exec.rs)と[待機時間の制限](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/unified_exec/mod.rs#L75-L78)で確認できます。外側の30秒という既定値は、[Code Mode の設定](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/config/mod.rs#L1113-L1127)に定義されています。

空入力の `write_stdin` には、[プロセス管理側で5秒の下限](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/unified_exec/process_manager.rs#L951-L960)が適用されます。`functions.wait` の10秒は、[Code Mode の既定値](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/code-mode-protocol/src/runtime.rs#L15-L16)と[引数省略時の処理](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/code_mode/wait_handler.rs#L25-L38)で確認できます。

継続待機で内側の `write_stdin` だけを40秒に延ばし、外側の `functions.exec` を既定の30秒にしておくと、内側の待機中に「JavaScript は実行中」という結果がモデルへ返る可能性があります。モデルは続きを待つために再び呼び出されます。

初回の内側・外側が両方30秒の場合は、ランタイム側の猶予が効くこともあります。v0.154.0 は10秒以上の外側待機に1秒の猶予を加え、その後にセッションの上限で制限します。今回の再測定にも、外側を既定値のままにして約30.2秒で直接完了したCIの例がありました。ただし、モデルが猶予を意識していたかは分からず、処理が猶予を超えれば外側が先に返り得ます。この猶予では内側40秒を収められないため、継続待機では外側の調整が必要です。[リリースの猶予処理](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/code-mode-runtime/src/service.rs#L192-L207)、[再測定の観測](../CODEX_WAITING_PRAGMA_REMOVAL_BENCHMARK.md)

秒数を固定しなくても、待機の長さと外側の待機時間の設定を指示する理由は2つあります。

1. **大小関係だけでは、待機が短すぎる問題が残ります。** 内側1秒・外側2秒でも大小関係は満たしますが、モデルによる確認や待機の指示が頻繁に発生します。待機だけが残った場面では、報告期限とツールの上限の範囲で、十分に長く待つことも必要です。
2. **外側の待機時間も設定する必要があります。** 初期のパッチでは、モデルが内側だけを延ばし、外側を既定値のままにする例がありました。現在の文面では、外側の `functions.exec` が内側の `exec_command` または `write_stdin` の待機に少しの余裕を加えた時間を確保するよう明記しています。設定構文は実行時のツール定義に委ね、ランタイム固有の構文を AGENTS.md に重複して書くことを避けています。[初期の調整経緯](../CODEX_WAITING_RUNTIME_PROMPT_BENCHMARK.md#investigation-and-prompt-tuning)

測定済みの旧版には、先頭行の `@exec` とキー `yield_time_ms` を指定する文言がありました。構文への言及を省いた現在の文面でも、6試験すべてで処理が完了し、外側の早期復帰はありませんでした。一方、直前の構文あり版よりモデル応答と入力トークンは増えています。構文を省けることと、トークン効率が同じであることは、それぞれ確認する必要があります。[現在の文面の再測定](../CODEX_WAITING_PRAGMA_REMOVAL_BENCHMARK.md)

共通ルールの45秒は待機時間の上限です。外側も毎回45秒にする必要はありません。初回の内側30秒に対して、実測では外側31秒や35秒でも、余分なセル再開を挟まずに結果を受け取れました。選んだ時間に十分な処理の余裕があるかは、実行環境によって変わります。

外側を45秒にしても、その時間を毎回使い切るわけではありません。内側の30秒の待機と前後処理が終わり、JavaScript が完了すれば、その時点で戻ります。初回の待機に必ず15秒が追加されることはありません。

待機時間を選ぶ際の基本条件は、次のとおりです。

```text
内側の待機時間 ＋ ラッパーの処理時間 ≤ 外側の待機時間
外側の待機時間 ＋ 前後の通信・モデル応答時間 ≤ 次の進捗報告までの残り時間
```

この範囲で内側を十分に長くし、不要なモデル呼び出しを減らします。前後の処理時間が増えたり、報告期限が近づいたりした場合は、待機時間を短縮します。ここで示した秒数は測定された設定の例で、どの環境でも余裕が足りるという保証はありません。

数値の明示が必要かどうかは、Astra／low・CLI 0.154.0・共有スキル無効の追加18試験で比較しました。結果を下表に示します。「数値なし」でも、待機枠や短い予備確認を避ける指示は残しています。既定値をそのまま使わせる条件ではありません。

| 比較した指示 | 数値なし→ありの応答回数 | 実際の待機引数と採用判断 |
| --- | ---: | --- |
| `exec_command: 30000` | 20→20（6組） | 全12試験で30秒を選択。明記による追加効果が確認できず、現在は秒数を省いている。 |
| `write_stdin: 40000` の追加 | 18→22（6組） | 数値なしでも40秒または44秒を選択。追加による削減は見られず、明示を見送った。 |
| `functions.wait: 45000` の追加 | 13→13（3組） | 全6試験で45秒を1回だけ呼び出した。追加効果が見られず、明示を見送った。 |

応答回数は試験全体の値です。各行は一部の試験を再集計しているため、足し合わせません。`functions.wait` の比較では、両条件で初回の外側だけを意図的に短くして実行中セルを発生させています。

初回30秒・外側45秒以外の組み合わせを網羅的に比較した結果ではありません。数値だけの明示を外しても今回の指示全体の効果が失われなかったことと、待機ルール自体が不要であることは区別する必要があります。区分別トークン、API単価換算額、実際の呼び出しは、[追加測定の報告書](../CODEX_WAITING_NUMERIC_OVERRIDES_BENCHMARK.md)に掲載しています。

### functions.exec と functions.wait の秒数を区別する

上表の `functions.wait: 45000` は、実行中セルの続きを待つ呼び出しへの具体値追加を指します。外側の `functions.exec` に渡す先頭行の `// @exec: {"yield_time_ms": 45000}` は、別の設定です。以前の18試験では、この外側45秒を全条件で残していました。

そこで、外側の45秒指定の有無と `functions.exec` の名指しの有無を切り分け、さらに12試験を行いました。全試験で外側だけが先に返る事象はなく、秒数を省いても、内側の待機を収める外側の設定が選ばれました。

名指しした数値なし版では、3試験のうち1試験でモデル応答が1回多くなりました。これは40秒の継続待機がコマンド完了の約0.31秒前に返った例です。名指しありの条件では、内側の待機時間に異なる選択も観測されました。名指しとの因果関係は未確定です。CIでの追加比較も含め、名指しした文面に応答削減の利点は見られず、測定時点では名指しを追加しない文面を選びました。[外側の比較と選定版の確認結果](../CODEX_WAITING_OUTER_EXEC_BENCHMARK.md)

その後、待機対象の関係が読み取りにくいという指摘を受け、2026年9月15日に配布用パッチを修正しました。外側・内側それぞれのツール名と、外側が実行中セルを返した場合に `functions.wait` を使うことを明記しています。また、先頭行の `@exec` という設定構文への言及を省き、待機時間の関係を指定する文面にしました。目的は指示を明確にし、設定構文の変更への依存を減らすことです。

この修正は、旧版・明確化した構文あり版・現在の構文なし版の3条件で、コマンド・CI・サブエージェントを各2回、計18試験で再測定しました。全件が受入条件を満たしました。構文あり版からなし版への変更では、入力が458,288→522,123トークンに増えた一方、API単価換算額は $1.110416→$1.086094 でした。安いキャッシュ読み出しの割合が増えたため、金額だけは下がっています。設定構文を省く方針で現在の文面を維持しますが、効率が変わらない、または全指標で優れているという推奨ではありません。[区分別カウンターと挙動の比較](../CODEX_WAITING_PRAGMA_REMOVAL_BENCHMARK.md)

### 継続待機の40秒を英語パッチで固定していない理由

**解説の40秒は、旧コンパクト版を適用した Astra が選んだ実測値です。** 現在の英語パッチも `write_stdin` に対して、`within budget`（報告期限までの待機枠に収める）と、Code Mode では外側が内側の待機と少しの余裕を含むことを求めています。外側45秒に対して内側40秒を選ぶと、ラッパーの処理に5秒の余裕を残せます。

初回の30秒は `exec_command` の実装上限、外側の45秒は60秒の報告間隔から選んだ待機枠です。継続待機の40秒は、その枠に収める選択肢の一つです。パッチでは内側の具体値をモデルに選ばせ、残り時間や処理の余裕に合わせて調整できる形にしています。

従来の実測では、40秒を明記しなくても、CI・サブエージェント・コマンドの各ケースで40秒の `write_stdin` が使われました。[最終パッチの実行記録](../waiting-benchmark/compact-final-astra-results/trial-evidence.json)

最初の追加比較でも、旧コンパクト版の通常コマンド3試験すべてで40秒が選ばれました。「通常は40秒、必要に応じて短縮」と明記した条件では、むしろ応答回数が増えた試験がありました。同じ40秒でも、通信や応答生成の所要時間によって75秒のコマンド完了まで届くかどうかが変わり、追加待機の要否が分かれています。このため、40秒の明示が悪化を引き起こすとは断定できませんが、追加を推奨する実測上の利点も得られませんでした。

現時点では、40秒をパッチに追加せず、外側の待機枠と処理の余裕に合わせて選ぶ指示を維持します。具体値を選ばせることによるばらつきは残ります。

### 実行中のセルは `functions.wait` で受け取り、その後に次のプロセス待機へ進む

それでも `functions.exec` が「セルは実行中」と返す場合は、そのセルの結果を `functions.wait` で待ちます。ここでいう「セル」は JavaScript の実行単位です。待機は共通の時間制限内で必要な長さを明示し、1秒刻みや未調整の既定値による再確認を避けます。

| 保持する ID | 続きを待つツール |
| --- | --- |
| コマンドの実行セッション ID | `write_stdin` |
| Code Mode の実行セル ID | `functions.wait` |

セルの中には、すでに実行中の `write_stdin` が残っているかもしれません。そのセルの結果を受け取る前に、同じプロセスへ別の確認を重ねると、待機が重複し、結果の管理も複雑になります。まずセルを最後まで受け取り、そこでコマンドがまだ続いていると分かった場合に、次のプロセス待機へ進みます。

## 4. CI and external work：CI や外部処理を待つ

### 対象のジョブを固定し、利用できる完了通知を優先する

待ち方は、利用できる機能に応じて「完了通知を待つ → 通知がなければ監視スクリプトを使う → スクリプト化が難しければ sleep を挟んで確認する」の順に選びます。以下で、それぞれの理由を説明します。

監視対象のジョブ ID を保持します。「最新の実行」だけを確認していると、別の実行や再試行を見てしまうことがあるためです。どの処理の結果を待ち、どの結果をもって完了とするかを一貫させます。

対象の完了通知を利用できるなら、それを優先し、状態が変わるまでの問い合わせを減らします。利用できる通知機能は、接続先の CI と Codex の連携方法に依存します。

### 状態確認をスクリプト化できるなら、上限のある監視処理を1つ動かす

通知がなくても状態取得コマンドを使えるなら、1つのシェル監視処理で繰り返し確認します。監視処理は既存のセッションとして保持し、長時間コマンドと同じ方法で待ちます。これにより、状態取得のたびにモデルが次の確認を指示する必要を減らせます。

監視には、**時間または確認回数の明示的な上限**を設けます。外部処理が停止したり、想定した完了状態にならなかったりした場合の、無制限な問い合わせを防ぎます。上限に達したら監視を一区切りとし、CI の成否は取得した状態から判断します。

出力は「実行中から完了へ変わった」「失敗が判明した」など、意味のある変化に絞ります。同じ状態を大量に出力すると、読むべきログが増え、途中でツールから制御が戻るきっかけも増え得るためです。

### 許容できる結果通知の遅れから確認間隔を選び、変化がなければ間隔を延ばす

確認間隔を延ばすほど問い合わせ回数を減らせますが、確認直後に処理が終わった場合は、その発見が次の確認まで遅れます。許容できる通知の遅れに合わせて確認間隔と上限を決め、状態が変わらなければその範囲でバックオフします。

この指示は、モデルが直接行う確認だけでなく、監視スクリプト内部の確認にも適用します。モデル応答を減らしても、監視スクリプトが外部サービスへ過剰に問い合わせていれば、外部サービス側の負荷や制限は改善しません。モデル応答回数と状態取得回数は別の指標です。

### 監視処理が現実的でなければ、利用可能な `clock.sleep` を挟む

`clock.sleep` は、「次の確認まで30秒待つ」といった時間待ちを Codex に直接依頼するツールです。通常は指定時間が経過すると戻り、実際に待った時間を返します。利用者からの新しい入力で早く戻る場合もあります。待機中に CI の状態を調べる機能はないため、完了確認には復帰後の状態取得が必要です。[sleep ツールの定義](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/handlers/sleep.rs#L43-L55)

`clock.sleep` は Codex の待機機構を直接使うため、シェルで `sleep 30` を実行する際のプロセス起動やセッション管理を省けます。状態確認をスクリプト化しにくい場合に、利用できる環境で、次の有用な確認まで間隔を空ける用途に使います。

たとえば30秒の sleep を始めて5秒後に CI が完了しても、その完了だけを理由に sleep は終了しません。新しい入力などによる中断がなければ、残り25秒と次の状態取得・回答の時間を経て、利用者に結果が届きます。

`wait_agent` など、通知や完了を検知できる待機の前後にさらに sleep を足すと、必要な結果を処理するまでの遅れを増やします。そのため、イベントに対応した待機には sleep を重ねません。

## 5. Results and goal state：結果とゴールの状態を正しく扱う

### 結果は速やかに処理し、必要な検証は残す

結果が届いたら、次の予定時刻まで待たずに処理します。コマンドの終了コードや必要なテスト結果など、依頼の完了に必要な検証も行います。

節約の対象は、結果が変わらない間の不要な確認です。確認すべき結果を読まない、検証を省く、途中で成功と報告するといった方法で使用量を減らすことは、このパッチの目的に含まれません。

### 観測のタイムアウトと、タスクの失敗を区別する

`wait_agent` のタイムアウト、プロセス実行中の `write_stdin` の復帰、監視スクリプトの上限到達だけでは、対象処理の失敗を判断できません。

待機が一区切りになった時点で、実際に得られた情報から次の行動を判断します。継続中なら必要な監視を続け、失敗が確認できたならその結果を処理します。観測期限だけを理由に正常な処理を中断・再実行することを避けます。

### `/goal` の長期外部待機では、一時停止の意向を一度確認し、実際の状態を確かめる

この項目は、`/goal` を使っている場合に適用します。`/goal` は、設定された目標に向けて作業の継続を管理する機能です。ゴールが有効なまま、残りが長時間の外部依存待ちだけになると、いったん最終応答を返しても、その後の継続処理でモデルが再開することがあります。

この長期の外部待機に入る場合に限り、一時停止するかをユーザーに一度確認します。質問や「待っています」という返答の後もゴールは有効なため、ユーザーの操作などで実際に一時停止されたことを確認します。

CLI 0.154.0 では、利用者が入力欄に `/goal pause` を送信して一時停止し、`/goal` を開いて `Status: paused` と表示されることを確認できます。依存していた処理が終わり、作業を再開できる状態になったら `/goal resume` を使います。一時停止で止まるのはゴールの自動継続です。外部の CI など、すでに動いている処理は個別に管理します。[ゴールの状態表示と操作](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/tui/src/chatwidget/goal_menu.rs#L87-L114)

使用量を止める目的で、作業の完了や障害の発生を偽ってはいけません。未完了のゴールを完了扱いにしたり、架空の障害を報告したりすると、タスクが放置され、利用者も状態を誤認します。停止が必要なら、正式な一時停止の操作を使います。

## 6. 実測で確認できた効果と、まだ確認していないこと

以下の表は、秒数を明記していた[旧コンパクト版](../waiting-benchmark/AGENTS.compact-final.md)の測定です。CLI 0.154.0 と GPT-6 Astra（以下 Astra）を使い、`effort: low` で、各75秒のコマンド・サブエージェント・CI 待機を1回ずつ実行しました。現在の文面の測定は[構文省略版の再測定報告](../CODEX_WAITING_PRAGMA_REMOVAL_BENCHMARK.md)に分けて掲載しています。

この比較ではスキルの影響を分けるため、共有スキルの指示と同梱スキルを無効にし、読み込みがなかったことも記録で確認しています。CI の状態確認にはローカルのシミュレーターを使い、コマンドと子エージェントは実際に実行しています。

比較対象は、先に測定した同じ CLI のパッチなしの結果です。親と子の使用量を合算しています。「結果通知の遅れ」は、処理の完了から最終回答の記録までの時間で、発見の遅れとモデルの応答時間を含みます。

| 待機対象 | モデル応答回数：導入前→後 | 入力トークン：導入前→後 | API 単価換算額：導入前→後 | 結果通知の遅れ：導入前→後 |
| --- | ---: | ---: | ---: | ---: |
| CI | 8→4 | 123,659→63,656 | $0.268036→$0.125336 | 11.00秒→27.34秒 |
| サブエージェント | 19→8 | 293,066→125,649 | $0.490254→$0.259968 | 7.01秒→6.99秒 |
| コマンド | 9→4 | 139,249→62,895 | $0.230692→$0.143288 | 4.79秒→8.22秒 |

合計では、モデル応答が36回から16回、キャッシュ分を含む入力が555,974から252,200トークン、API 単価換算額が $0.988982 から $0.528592 になりました。導入後の親エージェントの進捗報告間隔は、3件とも60秒以内でした。

ただし、CI の結果通知は約16秒遅くなり、状態取得回数も4回から6回に増えました。**モデル使用量の削減、外部への問い合わせ削減、結果通知の速さは、別々に評価する必要があります。**

金額は、サブスクリプションで報告されたトークン数に API の標準単価を当てた参考値です。Codex の実際の請求額ではありません。保存されたキャッシュ書き込みカウンターは0ですが、Codex は元の応答にその値がない場合も0で補います。そのため、実際の書き込みが0だったのか、値が未報告だったのかを区別できません。この換算では、記録された0をそのまま使っています。

この比較は、各条件1回の短時間測定を順に行った結果です。実行順序の無作為化は行っていません。次の範囲は未検証です。

- 追加比較で扱っていない個々の指示の削減寄与、長時間の実業務での安定した削減率。
- 現在の文面と旧コンパクト版の GPT-5.6 Sol での効果。それ以前の版でも Sol 全体で一貫した節約効果は確認できていません。
- 30分以上の待機でのキャッシュ維持効果や、このパッチによる `/goal` の使用量削減。
- 実際の CI サービスとの接続や、生成される監視スクリプトの失敗時の処理。

したがって、導入時には使用量だけでなく、結果が正しく返ること、通知の遅れ、外部への問い合わせ回数も合わせて確認します。上位の進捗報告要件や外部サービスの機能は、パッチだけでは変更できません。

## 7. AGENTS.md に追加する英語パッチ全文

以下が AGENTS.md に追記するパッチの全文です。コードブロック内の英語だけをコピーし、`${CODEX_HOME:-$HOME/.codex}/AGENTS.md` に追加してください。

```markdown
## Waiting for work

### Across all waits

Follow higher-priority instructions; do useful independent work first. When only waiting remains, put any required brief progress update in the same response before each blocking wait. For a 60-second update cadence, cap waits and wrapper yields at 45 seconds; shorten for tool limits or actionable deadlines. Use integer milliseconds. Updates alone do not justify status queries.

Longer waits may not reduce usage; add no cache-only keepalives without measured savings.

### Subagent results

When only subagent results remain, prefer direct `wait_agent` with `timeout_ms` within that budget.

### Terminal commands

When only command completion remains, start `exec_command` with a long `yield_time_ms` within tool limits and the budget. Retain its session; use empty `write_stdin` waits within budget, without preliminary short polls.

In Code Mode, set the outer `functions.exec` wait long enough to cover the inner `exec_command` or `write_stdin` wait plus a small margin, while staying within budget. If `functions.exec` returns a running cell, wait for that same cell with `functions.wait` using `yield_time_ms` within budget instead of 1-second/default checks; finish the cell before calling `write_stdin` again.

### CI and external work

Retain job identity; prefer completion notifications. Otherwise, if scriptable, use one shell watcher with an explicit time or check-count limit, retain its session, and emit only meaningful changes. Choose intervals for acceptable result delay; back off unchanged status.

If a watcher is impractical, use direct `clock.sleep` when available between useful checks. Do not add sleep around event-aware waits or assume it wakes on shell or CI completion.

### Results and goal state

Process results promptly; preserve required verification. Observation timeouts are not task failures.

If an active `/goal` would only wait on a prolonged external dependency, ask once about pausing; verify its state before treating it as paused. A final reply does not pause it. Never mark unfinished work complete or invent blockers to stop usage.
```
