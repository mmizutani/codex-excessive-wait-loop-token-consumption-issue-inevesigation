# Codex の待機時間：具体値の指定と Terminal commands 節の必要性

## TL;DR

- Astra／low・CLI 0.154.0・共有スキル無効で、数値指定の比較18件と節全体の削除比較12件、計30件を実測しました。すべて正常終了し、親エージェントの進捗報告の最大間隔は50.262秒でした。
- **`exec_command: 30000` の明記による応答削減効果は確認できませんでした。** `write_stdin: 40000` と `functions.wait: 45000` の追加にも利点が見られませんでした。その後の外側の比較も踏まえ、現在の配布版は個別の秒数指定を省いています。[最終選定と追加32試験](CODEX_WAITING_OUTER_EXEC_BENCHMARK.md)
- 数値比較では、具体値を省いても、他の待機指示は残しています。**「具体値なし」はランタイムの既定値をそのまま使わせる条件ではありません。** 外側の `functions.exec: 45000`、報告期限、短い予備確認を避ける指示は共通です。セル再開試験の初回だけは、両条件で外側を短くする診断用の指定を加えています。
- **`Terminal commands` 節は維持します。** 節の削除で短い予備確認が再発し、親子合計の応答は33→36回、入力は8.49%、API単価換算額は5.19%増えました。ただし、削除版の方が結果通知は早く、サブエージェントの応答数は同じでした。節の効果は限定的で、常に必要・常に安いと証明した結果ではありません。
- この文書の30試験は、秒数を明記した旧コンパクト版を対照にした記録です。外側の追加比較では、個別の秒数と名指し追加を省いた文面を選びました。現在の配布版には、2026年9月15日に外側・内側のツール名と `functions.wait` の役割を明記する修正を加えています。設定構文も省いた現在の文面は[別の18試験で再測定](CODEX_WAITING_PRAGMA_REMOVAL_BENCHMARK.md)しました。過去の試験結果は変更していません。

## 比較条件と評価方法

2026年9月14日、実際の Codex サブスクリプション認証を使ってモデルを呼び出しました。CLI はインストール済みの公式0.154.0、モデルは GPT-6 Astra、推論設定は `low` です。共有スキルの指示と同梱スキルを無効にし、読み込みがないことを各試験で確認しました。

各試験で新しい一時 `CODEX_HOME` と作業ディレクトリを作り、同じモデルカタログと75秒のコマンドを使います。認証情報は一時ディレクトリ内に限定し、試験後に削除しています。モデル応答のモックは使っていません。

条件を固定シードで並べ替え、各反復内で最大2件を並行実行しました。反復間は前の全試験が終わるまで待ちます。比較対象も今回新たに実行しており、以前の測定値は対照に流用していません。キャッシュの状態、バックエンド、通信やモデル応答の時間は完全には固定できません。[事前計画](../waiting-benchmark/numeric-waits/PLAN.md)、[実行順序とプロンプトのハッシュ](../waiting-benchmark/numeric-waits/isolated-manifest.json)

| 比較 | 条件 | 反復数 | 試験数 |
| --- | --- | ---: | ---: |
| 通常のコマンド待機 | `exec_command` の30秒指定あり／なし × `write_stdin` の40秒指定あり／なし | 各3回 | 12 |
| 実行中の Code Mode セルの再開 | `functions.wait` の45秒指定あり／なし。他の指示は旧対照版と同じ | 各3回 | 6 |

`exec_command` の具体値を省く条件では、ツールの上限と報告期限に収まる長い待機を指示しました。`write_stdin` と `functions.wait` の具体値を省く条件は、現行パッチの定性的な待機指示です。数値を指定する条件でも、報告期限に合わせた短縮を許可しています。[比較した指示文](../waiting-benchmark/numeric-waits/README.md)

通常のコマンド待機では `functions.wait` が呼ばれないことがあるため、セル再開の試験では最初の `functions.exec` だけを1 msで返すよう指定しました。その内側では実際のコマンドを30秒待ち、実行中セルの結果を `functions.wait` で受け取ります。この初回コードは両条件で同じです。セルが実行中になる状況を意図的に作った診断であり、その状況が実務でどの程度発生するかは測っていません。

評価では、正しい最終結果、コマンドの単一起動、終了コード0、期待した子エージェント数、実際のモデル・推論設定、スキルの未使用を確認しました。応答IDで使用量を重複排除し、各セッションの応答別トークン数と累計値も照合しています。結果の通知遅延と進捗報告間隔は、メッセージ記録のタイムスタンプで測定しました。

18件の合計は、66応答、入力1,039,195トークン（通常148,315、キャッシュ読み出し890,880、記録上の書き込み0）、出力3,523トークン、API単価換算額 **$2.550180** でした。調査・レビュー用エージェントの使用量は、この試験合計に含めていません。

### exec_command：30秒を明示しなくても、全試験で30秒が選ばれた

他の条件を対応させた6組では、数値なし・ありの合計応答数は **20回・20回** でした。通常のコマンド試験12件すべてで、実際の初回引数は `yield_time_ms: 30000` でした。今回の残りの指示があれば、モデルは具体値が書かれていなくても30秒を選べています。

合計換算額は $0.813084・$0.704254 と異なりますが、入力合計は313,826・313,892でほぼ同じです。キャッシュ差を主因とする金額差から、数値の明示によって節約できたとは判断できません。

30秒を明記する表現が比較した代替文より短いことは、数値の効果を示す根拠にはなりません。待機時間を選ぶ条件があれば30秒を明示する必要性は示されなかったため、現在の配布版ではこの固定値を省いています。

### write_stdin：40秒の追加による削減は見られなかった

初回の指定条件を対応させた6組では、数値なし・ありの合計応答数は **18回・22回**、入力合計は281,950・345,768、換算額は $0.719726・$0.797612 でした。応答数は4組で増え、2組で同じでした。平均通知遅延も、40秒を加えた条件で約2秒長くなっています。

ただし、これを40秒指定だけによる悪化と断定することもできません。旧対照版も通常コマンドの3試験すべてで40秒を選んでいます。同じ40秒でも、通信やモデル応答時間の差によって75秒のコマンド完了に届くかどうかが変わり、追加確認の要否が分かれました。両方の具体値を省いた3試験では44秒が選ばれ、いずれも1回の継続待機で完了しました。

今回の目的に対して、40秒の明示を追加する利点は確認できませんでした。外側の待機枠と報告期限に合わせて内側を選ぶ旧対照版の指示を維持します。44秒の方が常に有利だと示した結果でもなく、処理の余裕と通知遅延の評価は引き続き必要です。

### functions.wait：両条件とも45秒を1回だけ呼び出した

セル再開の6試験すべてで、実際の `functions.wait` は **45秒指定・1回** でした。1回の応答で待機を指示できており、数値追加によって減らせる再確認は観測されませんでした。

試験全体の合計応答数も13回・13回です。個別の反復では4回と5回が入れ替わっていますが、その差はセル再開後の `write_stdin` がコマンド完了直前で返ったかどうかによるものです。`functions.wait` の効率差には帰属できません。

換算額は $0.425090・$0.607752 でした。入力合計と出力はほぼ同じで、金額差の大部分はキャッシュ読み出し割合の違いです。数値追加が高コスト化を引き起こしたという根拠にはなりません。追加効果が確認できなかったため、旧対照版の待機枠指定を維持します。[実際の引数と待機回数](../waiting-benchmark/numeric-waits/isolated-results/COMPARISON.md)

上の3つの比較は、一部の試験を異なる観点で再集計しています。各比較の合計を足し合わせないでください。重複のない総計は18件の合計です。

## Terminal commands 節全体を削除する比較

ユーザーから追加された問いに対応し、旧対照版と、この節だけを削除した版を比較しました。通常コマンド・CI監視・サブエージェントの各条件を2回ずつ実行する、別の12件です。数値比較の対照は流用せず、すべて新規に実行しました。[追加計画](../waiting-benchmark/numeric-waits/PLAN.md#user-requested-extension-remove-the-entire-terminal-section)、[削除版](../archive/agents-patches/waiting-benchmark/numeric-waits/prompts/AGENTS.no-terminal.md)

削除版にも、共通ルールの「待機とラッパーは45秒以内」、サブエージェントの直接待機、CIの監視スクリプトなどの指示は残っています。削除により、初回30秒、短い予備確認の回避、外側の具体的な設定書式、セル再開の順序などがまとめてなくなります。

全12件が受入確認を通過し、親の報告間隔は旧対照版で最大48.515秒、削除版で最大50.262秒でした。ただし、削除版の通知は、CIで平均14.48秒、サブエージェントで5.42秒、コマンドで4.33秒速くなっています。この通知速度の差は、待機の区切り、監視間隔、モデルの応答時間を含む結果です。節を残す方がすべての指標で優れるわけではありません。

### 実際に変わった待ち方

- 旧対照版では、6件すべてで長時間コマンドまたは監視処理の初回を30秒、継続待機を40秒、外側を45秒にしました。短い予備確認はありませんでした。
- 削除版では、6件すべてで初回を1秒に戻しました。うちCIの1件と通常コマンドの1件では、直後に `write_stdin: 1000` の予備確認も入っています。ランタイムが空入力の下限5秒へ補正するため、実際の待機は約5秒ですが、その後にモデルが待ち方を判断し直しています。
- 削除版も、その後は共通ルールに沿って45秒の継続待機へ移りました。共通ルールだけで抑えられている部分もあります。ただし、外側・内側をともに45秒にして処理の余裕を取らない呼び出しでした。今回は外側だけが先に返る事象は発生しておらず、その点のコスト増加は観測していません。
- CIでは、両条件とも上限のある監視処理を使い、2試験合計の実際の状態取得回数も9回ずつでした。モデル応答数が増えたのは、状態取得回数の増加とは別の問題です。予備確認に加え、旧対照版の1件は最初の状態取得と監視開始を同じコマンドにまとめ、削除版は別々に起動していました。CIの差すべてを待機時間だけに帰属することはできません。
- サブエージェントでは、親が両条件とも `wait_agent: 45000` を使い、親8回・子8回で合計16応答でした。子のコマンドの待ち方は変わっても、今回の全体の応答数は変わりませんでした。削除版の1件は子へ渡す履歴を `fork_turns: "1"` とし、残り3件の `"all"` と異なります。小さなトークン・金額の減少を、待ち方だけの効果とは判断できません。

[実際の引数一覧](../waiting-benchmark/numeric-waits/section-results/COMPARISON.md)、[全呼び出しと出力](../waiting-benchmark/numeric-waits/section-results/trial-evidence.json)

### 採用判断：節は残し、数値指定を増やさない

共通ルールの「45秒以内」は上限だけを示すため、1秒の初回待機や短い予備確認も許す形になっています。`Terminal commands` 節は、長時間コマンドで上限に近い待機を使い、同じ実行を順序立てて待つよう補います。CIのシェル監視処理や、子エージェントが実行するコマンドにも適用されます。

今回の結果では、節を削除すると短い予備確認が再発し、トークン削減にもつながりませんでした。**待機中の不要なモデル呼び出しを抑えるという目的に対して、旧対照版の節を残す判断です。** 差は小さく、各条件2回の結果から節内の全文章が不可欠とは言えません。旧対照版の継続待機も完了直前で返ることがあり、最小コストを保証する指示ではありません。

数値の比較では `write_stdin: 40000` と `functions.wait: 45000` を追加する利点が確認できず、`exec_command: 30000` の明記にも応答削減効果が見られませんでした。外側の追加比較も経て、[現在の配布用パッチ](../guides/AGENTS.waiting-compatible.md)では、節の待機条件を残しつつ個別の秒数を省いています。[最終選定の報告](CODEX_WAITING_OUTER_EXEC_BENCHMARK.md)と[日本語解説](../guides/AGENTS.waiting-explanation.ja.md)に反映済みです。

## 今回の測定総量

2つの段階を合わせて、重複のない30試験・135応答です。入力2,125,797トークン（通常247,653、キャッシュ読み出し1,878,144、記録上の書き込み0）、出力8,716トークン、API単価換算額 **$4.790474** でした。

区分別の換算額は、通常入力 $2.476530、キャッシュ読み出し $1.878144、書き込み $0、出力 $0.435800 です。従来報告の73試験、および今回の調査・レビュー用エージェントの使用量は含みません。

独立レビュー用のサブエージェントにも、会話履歴を渡さずに測定方法と証拠の照合を依頼しました。全30試験の応答ID、カウンターの照合、受入確認、実際の引数を再確認し、数値比較のキャッシュ差、5秒へ補正された予備確認、子に渡す履歴の差などを解釈へ反映しています。

## 検証の限界

- 対象は Astra／low・CLI 0.154.0 の短時間待機です。Sol、別の推論設定、長時間の実業務での効果は測っていません。
- 数値比較は具体値の追加・削除を評価しています。数値を40秒から別の秒数へ網羅的に変える最適化実験は行っていません。
- キャッシュやバックエンドの条件は完全には固定できません。応答数と実際の引数が同じ場合の金額差を、そのままプロンプトの効果と解釈しません。
- CIはローカルの状態シミュレーターです。実際のCIサービスの障害処理や通知連携を検証する実験は含みません。
- 進捗報告間隔は完了したメッセージの記録で測ります。利用者に最初の文字が表示される時刻とは異なります。
