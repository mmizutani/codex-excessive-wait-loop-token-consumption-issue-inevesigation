# Codex の待機ルール：各指示の理由と期待する効果

対象は、2026年9月14日時点の最終コンパクト版 [AGENTS.waiting-compatible.md](AGENTS.waiting-compatible.md) です。Codex CLI 0.154.0 で測定した [AGENTS.compact-final.md](../waiting-benchmark/AGENTS.compact-final.md) と同じ内容を、末尾に全文掲載しています。

## TL;DR

- このパッチは、完了確認・進捗報告・必要な検証を続けながら、**状態が変わっていないのにモデルが何度も判断する機会を減らす**ための指示です。対象はサブエージェント、長時間コマンド、CI などの外部処理です。
- 完了を検知できる待機ツールを優先し、コマンドとその外側の実行ラッパーの待機時間をそろえます。進捗報告が必要な場合は、そのための時間も確保します。
- 長く待てば必ず安くなるわけではありません。確認間隔を延ばすと結果の通知が遅れることがあり、キャッシュ維持だけのアクセスにもコストがかかります。
- 最終版の短時間の Astra 比較では、入力トークンが **54.64%**、API 単価による換算額が **46.55%** 減りました。ただし CI の結果通知は約16秒遅くなりました。実際の契約料金の削減や、すべての業務での同じ効果を保証する結果ではありません。

## なぜ「待つだけ」で使用量が増えるのか

コマンドや CI が実行中であっても、待機ツールの内部で待っている時間に比例して、モデルが出力を生成し続けるわけではありません。使用量が増える主な経路は、待機が何度も短く区切られ、そのたびにモデルへ制御が戻ることです。

たとえば「まだ実行中」という結果を受け取るたびに、モデルが状況を読み、次の確認を指示すると、情報がほとんど増えていなくても新たな推論が発生します。その際には会話の履歴も入力に含まれます。入力の一部がキャッシュされていても、読み出しや新規入力・出力のコストがなくなるわけではありません。

パッチは、この反復を減らすようにツールの使い方を指定します。モデルが書いた監視スクリプトの内部で状態を確認することと、確認のたびにモデルへ戻ることは区別します。また、親エージェントが効率よく待っていても、子エージェントが細かい確認を繰り返せば、全体の使用量は増えます。

ここでいう「モデルへの応答要求1回」は、ユーザーとの会話1往復とは異なります。1つの依頼を処理する間に、ツールの呼び出しと結果の受け取りを挟んで、何回もの応答要求が発生します。

## 適用方法

末尾の英語パッチを、グローバルな `${CODEX_HOME:-$HOME/.codex}/AGENTS.md` に追加します。`CODEX_HOME` を設定していなければ、通常は `~/.codex/AGENTS.md` です。既存の指示は残し、以前の待機ルールがあれば同じ節を置き換えて、重複を避けます。適用後は新しいセッションで利用します。

この日本語の説明全文を AGENTS.md に入れる必要はありません。説明は利用者向けの資料として保管し、エージェントには短いパッチを渡します。パッチ自体にスキルの導入は不要です。

以下はパッチの各節に対応しています。「期待する効果」は指示の設計意図です。各指示を一つずつ外す実験はしていないため、項目ごとの削減量が実証されているという意味ではありません。

## 1. Across all waits：すべての待機に共通する指示

### 上位の指示に従い、先に独立した作業を進める

AGENTS.md の追加指示は、システムや開発者の指示より優先されません。たとえば上位の指示で定期的な進捗報告が求められている場合、このパッチを理由に報告を省略することはできません。冒頭で優先順位を明示するのは、待機による節約と既存の動作要件を両立させるためです。

待っている結果に依存しない必要な作業があれば、先に進めます。たとえばテストの完了を待つ間に、依頼の範囲内で変更箇所をレビューできます。結果が必要になるまで他の作業を進めることで、待機だけを目的としたやり取りを減らせます。

### 必要な進捗報告は、待機ツールを呼ぶ同じ応答に含める

残っている作業が待機だけで、進捗報告が必要なら、「処理は継続中です。完了を待ちます」などの短い報告に続けて、同じモデル応答で待機ツールを呼びます。

これにより、報告だけの応答と、次の待機を指示する応答を分ける必要を減らします。ただし、報告文そのものの出力トークンは発生しますし、必要な報告のためにモデルが再開する機会も残ります。報告が不要な状況で、常に報告を増やす指示ではありません。

### 60秒ごとの報告が必要なら、待機とラッパーの上限を45秒にする

ツールで60秒いっぱい待つと、その前後の通信やモデルの応答時間が加わり、次の報告が60秒を超えやすくなります。そこで、60秒の報告間隔に対しては1回の待機を45秒以内にし、残り約15秒を余裕として確保します。

これは遅延の上限保証ではありません。ツールの制限、次に対応すべき期限、実際の応答時間によって、さらに短くする必要があります。45秒はこの報告条件に合わせた目安であり、すべての環境に一律で最適な待機時間ではありません。

また、**待機時間の指定は、毎回その秒数を待ち切るという意味ではありません。** 完了や通知を検知できるツールなら、それを受けて早く戻れる場合があります。後述する単純な `clock.sleep` とは、この点が異なります。

### ミリ秒は整数で指定する

`30000` は30秒、`45000` は45秒です。待機ツールには整数として引数を検証する経路があるため、`45000.0` のような小数表記を避けます。引数エラーと、その修正のための余分なやり取りを防ぐ狙いです。

### 進捗報告のためだけに、状態確認を追加しない

「ユーザーへ報告する時刻になった」ことと、「外部の状態を再確認する必要がある」ことは別です。すでに実行中のコマンドや監視処理があり、新しい結果を受け取っていなければ、その観測範囲を短く報告できます。

報告のたびにエージェント一覧、コマンド状態、CI の状態を追加取得すると、情報が変わっていなくてもツール呼び出しやモデル応答が増えます。この指示は、その追加確認を抑えるものです。未確認の状態を確認済みとして報告してよい、という意味ではありません。

### キャッシュ維持だけのアクセスは、節約効果を測るまで追加しない

確認回数を減らすと入力の再送を減らせる一方、長い間隔を空けた後のキャッシュ状態によって、次の応答のコストは変わり得ます。しかし、キャッシュを維持するためだけにモデルを呼び出しても、キャッシュ読み出し、新規入力、出力のコストが発生します。

仮に「30分」をキャッシュ寿命の前提にしても、それだけで「25分ごとに維持アクセスを入れると安い」とは判断できません。この調査では、Codex サブスクリプションにおける30分の保証や、期限をまたぐ待機のコストを独立に確認していません。

そのため、パッチはキャッシュを無視せず、同時に未測定の維持アクセスも勧めません。60秒ごとの進捗報告などで通常のモデル呼び出しが続いている場合は、その活動とは別にキャッシュ維持ループを追加する理由もありません。

## 2. Subagent results：サブエージェントの結果を待つ

サブエージェントは、親エージェントから依頼された作業を別に実行するエージェントです。独立した作業を終え、残りがその結果だけなら、直接 `wait_agent` を使います。これはエージェントからの通知やメッセージを待つ仕組みです。短い間隔で状態一覧を取得し続けるより、モデルが判断し直す回数を減らすことを狙っています。

`timeout_ms` は、共通ルールの待機時間の範囲に収めます。60秒ごとの報告が必要な環境では、たとえば `45000` です。通知やメッセージで待機が早く終わる場合もありますが、届いた内容がタスク完了を意味するかは別途判断します。

タイムアウトは「指定した観測時間が終わった」という意味です。それだけで子エージェントの失敗や停止を判断したり、同じ作業を別の子にやり直させたりしないことが、最後の結果処理ルールにもつながります。

## 3. Terminal commands：長時間コマンドを待つ

### 最初から適切な長さで待ち、同じ実行セッションを使い続ける

残りがコマンドの完了だけなら、`exec_command` の初回呼び出しを `yield_time_ms: 30000`、つまり最大30秒の観測として開始します。報告の期限やツールの制限がそれより短ければ、短縮します。

最初に短時間で戻り、直後に「まだ実行中か」を再確認する流れを避けるための指定です。コマンドが早く終われば結果を受け取れますし、続いていれば実行セッションの ID を保持して、その同じ処理を待ちます。

継続待機では、`write_stdin` の `chars` を空文字列 `""` にします。入力を送らずに、既存のプロセスの出力や終了を待つ使い方です。初回の直後に予備的な短い確認を挟まず、必要な長さの待機に進みます。これにより、余分なモデル応答とコマンドの重複実行を避けます。

### コードモードでは「内側」と「外側」の待機時間を合わせる

コードモードでは、`functions.exec` が JavaScript を実行し、その中から `exec_command` や `write_stdin` を呼び出します。このため、待機には次の2つの層があります。

| 層 | 待っているもの | 指定例 |
| --- | --- | --- |
| 内側：`write_stdin` | 実行中コマンドの出力・終了 | `yield_time_ms: 40000` |
| 外側：`functions.exec` | 上記のツール呼び出しを含む JavaScript の実行 | 先頭行の `// @exec: {"yield_time_ms": 45000}` |

内側を40秒にしても、外側がそれより先に制御を戻すと、モデルは途中で外側の実行を再び待つ必要があります。この追加の応答を減らすため、外側が内側の待機と少しの余裕を覆うようにします。

パッチが先頭行の書式まで明示するのは、「待機時間をそろえる」という抽象的な指示だけでは、その設定が実際の呼び出しに反映されない例があったためです。**初回の30秒と外側の45秒はパッチの指定値、継続待機の40秒は余裕を確保した実測例**です。いずれも共通の報告期限やツール制限に合わせて短縮します。

### 実行中のセルは `functions.wait` で受け取り、その後に次のプロセス待機へ進む

それでも `functions.exec` が「セルは実行中」と返す場合は、そのセルの結果を `functions.wait` で待ちます。ここでいう「セル」は JavaScript の実行単位です。待機は共通の時間制限内で必要な長さを明示し、1秒刻みや未調整の既定値による再確認を避けます。

| 保持する ID | 続きを待つツール |
| --- | --- |
| コマンドの実行セッション ID | `write_stdin` |
| コードモードの実行セル ID | `functions.wait` |

セルの中には、すでに実行中の `write_stdin` が残っているかもしれません。そのセルの結果を受け取る前に、同じプロセスへ別の確認を重ねると、待機が重複し、結果の管理も複雑になります。まずセルを最後まで受け取り、そこでコマンドがまだ続いていると分かった場合に、次のプロセス待機へ進みます。

## 4. CI and external work：CI や外部処理を待つ

### 対象のジョブを固定し、利用できる完了通知を優先する

監視対象のジョブ ID を保持します。「最新の実行」だけを確認していると、別の実行や再試行を見てしまうことがあるためです。どの処理の結果を待ち、どの結果をもって完了とするかを一貫させます。

対象の完了通知を利用できるなら、それを優先します。通知が届く仕組みがあれば、状態が変わるまで何度も問い合わせる必要を減らせます。パッチ自体が、通知機能のない CI に新しい通知機能を追加するわけではありません。

### 状態確認をスクリプト化できるなら、上限のある監視処理を1つ動かす

通知がなくても状態取得コマンドを使えるなら、1つのシェル監視処理で繰り返し確認します。監視処理は既存のセッションとして保持し、長時間コマンドと同じ方法で待ちます。これにより、状態取得のたびにモデルが次の確認を指示する必要を減らせます。

監視には、**時間または確認回数の明示的な上限**を設けます。外部の処理が停止したり、想定した完了状態にならなかったりしても、無制限に問い合わせ続けることを防ぎます。この上限は監視の区切りであり、CI の失敗を宣言する条件ではありません。

出力は「実行中から完了へ変わった」「失敗が判明した」など、意味のある変化に絞ります。同じ状態を大量に出力すると、読むべきログが増え、途中でツールから制御が戻るきっかけも増え得るためです。

### 許容できる結果通知の遅れから確認間隔を選び、変化がなければ間隔を延ばす

確認間隔を延ばすほど問い合わせ回数を減らせますが、確認直後に処理が終わった場合は、その発見が次の確認まで遅れます。結果をどの程度早く受け取りたいかを基準に、間隔とその上限を決めます。状態が変わらなければ、その範囲で段階的に間隔を延ばします。これが「バックオフ」です。

この指示は、モデルが直接行う確認だけでなく、監視スクリプト内部の確認にも適用します。モデル応答を減らしても、監視スクリプトが外部サービスへ過剰に問い合わせていれば、外部サービス側の負荷や制限は改善しません。モデル応答回数と状態取得回数は別の指標です。

### 監視処理が現実的でなければ、利用可能な `clock.sleep` を挟む

状態確認をスクリプト化しにくい場合は、意味のある確認の間に直接 `clock.sleep` を使います。ただし、このツールが利用できる場合に限ります。パッチは、すべての利用者に `sleep_tool` の `always_on` 設定を必須とするものではありません。

`clock.sleep` は、シェルや CI の完了通知を受け取るための仕組みではありません。処理が途中で終わっても、それを理由に自動で待機が解けるとは限りません。結果を発見するのは、原則として次の確認時です。

一方、`wait_agent` など、通知や完了を検知できる待機の前後にさらに sleep を足すと、必要な結果を処理するまでの遅れを増やします。そのため、イベントに対応した待機には sleep を重ねません。

## 5. Results and goal state：結果とゴールの状態を正しく扱う

### 結果は速やかに処理し、必要な検証は残す

結果が届いたら、次の予定時刻まで待たずに処理します。コマンドの終了コードや必要なテスト結果など、依頼の完了に必要な検証も行います。

節約の対象は、結果が変わらない間の不要な確認です。確認すべき結果を読まない、検証を省く、途中で成功と報告するといった方法で使用量を減らすことは、このパッチの目的に含まれません。

### 観測のタイムアウトと、タスクの失敗を区別する

`wait_agent` の観測時間が終わること、プロセスが実行中のまま `write_stdin` が戻ること、監視スクリプトが確認回数の上限に達することは、対象の処理が失敗した証拠ではありません。

待機が一区切りになった時点で、実際に得られた情報から次の行動を判断します。継続中なら必要な監視を続け、失敗が確認できたならその結果を処理します。観測期限だけを理由に正常な処理を中断・再実行することを避けます。

### `/goal` の長期外部待機では、一時停止の意向を一度確認し、実際の状態を確かめる

`/goal` は、設定されたゴールに向けて作業の継続を管理する機能です。ゴールが有効なまま、残りが長時間の外部依存待ちだけになると、いったん最終応答を返しても、その後の継続処理でモデルが再開することがあります。

そこで、この状況に限って、一時停止するかをユーザーに一度確認します。短い待機のたびに許可を求める指示ではありません。また、質問したことや「待っています」と返答したこと自体では、ゴールは停止しません。ユーザーの操作などで実際に一時停止したと確認できるまでは、停止した扱いにしません。

最後の禁止事項は、使用量を止めるために完了やブロック状態を偽らない、というものです。未完了のゴールを完了にしたり、存在しない障害を申告したりすると、依頼が放置され、利用者も状態を誤認します。停止が必要なら、状態を正しく保つ正式な一時停止として扱います。

## 6. 実測で確認できた効果と、まだ確認していないこと

最終コンパクト版では、CLI 0.154.0、GPT-6 Astra、推論量の設定である `effort` を `low` にした条件で、各75秒のコマンド・サブエージェント・CI 待機を1回ずつ実行しました。共有スキルの指示と同梱スキルを無効にし、スキルの読み込みがなかったことを記録でも確認しています。CI は実際の外部 CI サービスではなく、ローカルの状態シミュレーターです。コマンドと子エージェントは実際に実行しています。

比較対象は、先に測定した同じ CLI のパッチなしの結果です。親と子の使用量を合算しています。「結果通知の遅れ」は、処理の完了から最終回答の記録までの時間で、発見の遅れとモデルの応答時間を含みます。

| 待機対象 | モデル応答回数：導入前→後 | 入力トークン：導入前→後 | API 単価換算額：導入前→後 | 結果通知の遅れ：導入前→後 |
| --- | ---: | ---: | ---: | ---: |
| CI | 8→4 | 123,659→63,656 | $0.268036→$0.125336 | 11.00秒→27.34秒 |
| サブエージェント | 19→8 | 293,066→125,649 | $0.490254→$0.259968 | 7.01秒→6.99秒 |
| コマンド | 9→4 | 139,249→62,895 | $0.230692→$0.143288 | 4.79秒→8.22秒 |

合計では、モデル応答が36回から16回、キャッシュ分を含む入力が555,974から252,200トークン、API 単価換算額が $0.988982 から $0.528592 になりました。導入後の親エージェントの進捗報告間隔は、3件とも60秒以内でした。

ただし、CI の結果通知は約16秒遅くなり、状態取得回数も4回から6回に増えました。**モデル使用量の削減、外部への問い合わせ削減、結果通知の速さは、別々に評価する必要があります。**

金額は、サブスクリプションで報告されたトークン数に API の標準単価を当てた参考値です。Codex の実際の請求額ではありません。キャッシュ書き込みの実数は個別に取得できず、報告・既定値のゼロとして計算しています。

この比較は各条件1回の短時間測定で、対照と導入後を同時に無作為化して実行したものではありません。次の範囲は実証していません。

- 個々の指示の削減寄与、長時間の実業務での安定した削減率。
- 最終コンパクト版の Sol での効果。以前の版でも Sol 全体で一貫した節約効果は確認できていません。
- 30分以上の待機でのキャッシュ維持効果や、このパッチによる `/goal` の使用量削減。
- 実際の CI サービスとの接続や、生成される監視スクリプトの失敗時の処理。

したがって、導入時には使用量だけでなく、結果が正しく返ること、通知の遅れ、外部への問い合わせ回数も合わせて確認します。上位の進捗報告要件や外部サービスの機能は、パッチだけでは変更できません。

```markdown
## Waiting for work

### Across all waits

Follow higher-priority instructions; do useful independent work first. When only waiting remains, put any required brief progress update in the same response before each blocking wait. For a 60-second update cadence, cap waits and wrapper yields at 45 seconds; shorten for tool limits or actionable deadlines. Use integer milliseconds. Updates alone do not justify status queries.

Longer waits may not reduce usage; add no cache-only keepalives without measured savings.

### Subagent results

When only subagent results remain, prefer direct `wait_agent` with `timeout_ms` within that budget.

### Terminal commands

When only command completion remains, start `exec_command` with `yield_time_ms: 30000`, shortened to the budget. Retain its session; use empty `write_stdin` waits within budget, without preliminary short polls.

In code mode, set first-line `// @exec: {"yield_time_ms": 45000}`, adjusted to budget, covering the inner wait plus a small margin. Resume running cells with `functions.wait` within budget instead of 1-second/default checks; finish the cell before polling the process again.

### CI and external work

Retain job identity; prefer completion notifications. Otherwise, if scriptable, use one shell watcher with an explicit time or check-count limit, retain its session, and emit only meaningful changes. Choose intervals for acceptable result delay; back off unchanged status.

If a watcher is impractical, use direct `clock.sleep` when available between useful checks. Do not add sleep around event-aware waits or assume it wakes on shell or CI completion.

### Results and goal state

Process results promptly; preserve required verification. Observation timeouts are not task failures.

If an active `/goal` would only wait on a prolonged external dependency, ask once about pausing; verify its state before treating it as paused. A final reply does not pause it. Never mark unfinished work complete or invent blockers to stop usage.
```
